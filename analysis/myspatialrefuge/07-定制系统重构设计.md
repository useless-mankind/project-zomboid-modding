## 2. 两个对本次重构极其有利的既有事实

### 2.1 ✅ `SpatialWell.Find` 已经是「世界对象为事实源」的形状 → **不需要动存档**

`[文件] MSR_SpatialWell.lua:309-355`：

```
findAtState(refugeData)          -- 快速路径：读 customizations.spatialWell 的 x/y，去那个格子找
  └─ 找不到 / 没记录
       └─ World.iterateArea(...)  -- 回退路径：扫整个庇护所区域，按 ModData 标记重建
```

也就是说 **`refugeData.customizations.x` 只是索引/缓存，真正的"这座建筑存在"由世界对象的 ModData 决定**，而且已经有"丢失就从世界重建"的能力。

**结论**：把每座建筑的索引统一成 `customizations.<buildableId>`，**shape 与现在的 `customizations.spatialWell` 完全一致**，因此：

- **井的现有存档零影响**（键名不变）
- **不需要 `CURRENT_DATA_VERSION` 迁移**
- 新建筑只是多一个键

### 2.2 ✅ 保护名单不用改

`MSR_Context.lua:249` 的保护判定是 `md.isSacredRelic or md.isRefugeBoundary or md.isProtectedRefugeObject or md.isSpatialWell` —— 而 `tagWell` 已经给井打了 `md.isProtectedRefugeObject = true`（`MSR_SpatialWell.lua:391`）。

**所以泛化后这个判定不必修改**，新建筑只要打上 `isProtectedRefugeObject` 就自动受保护。

## 3. 目标设计

### 3.1 核心思路：注册表（数据 + 3 个回调），面板与光标全部泛化

```
                    ┌──────────────────────────────┐
                    │  MSR_BuildableData (新增)     │  ← 每个建筑一条注册项
                    │  id / 名称 / 描述 / 图标 /     │
                    │  cost / 属性行 / 上限 /        │
                    │  canPlaceAt / canMoveTo /      │
                    │  createAt / find / objectTag   │
                    └──────────────┬───────────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
┌────────────────┐      ┌──────────────────┐      ┌────────────────────┐
│ MSR_BuildCursor│      │ MSR_BuildableLogic│     │ MSR_Customization  │
│ (光标, 泛化)    │      │ (事务化建造/移动)  │     │ Panel (列表+详情)   │
│ isValid→canPlace│     │ Begin→校验→扣料→   │     │ 全部读注册表        │
│ tryBuild→Build │      │ createAt→提交/回滚 │     │ 不再有任何井字面量   │
└────────────────┘      └──────────────────┘      └────────────────────┘
```

**每加一个新建筑 = 在注册表里加一条 + 补翻译**，不再复制面板或光标。

### 3.2 注册项骨架（以水井为第一个条目，完全等价现有行为）

```lua
-- shared/MSR_BuildableData.lua
MSR.BuildableData.Register({
    id          = "spatial_well",
    name        = "UI_SpatialWell_Name",          -- 复用现有翻译，不动
    description = "UI_SpatialWell_Description",
    description2= "UI_SpatialWell_Description2",
    icon        = "media/ui/SpatialWell_64x64.png",
    sortOrder   = 10,
    maxPerRefuge= 1,                              -- 1 = 单实例（井）；nil/0 = 不限个

    objectTag   = "isSpatialWell",                -- ★ 保持原名 → 旧档的井仍能被找到
    moveCooldown= 30,

    -- 成本：与升级/兑换同构，直接喂给 Transaction.Begin
    cost = {
        { type = "Base.MagicalCore",     count = 35 },
        { type = "Base.MetalPipe",       count = 4  },
        { type = "Base.ConcretePowder",  count = 1  },
        { type = "Base.BucketEmpty",     count = 1,
          substitutes = {...}, predicate = MSR.SpatialWell.IsEmptyBucket },
    },

    -- 详情面板里的属性行（数据驱动，不再是写死的 4 行）
    properties = {
        { label = "UI_SpatialWell_Capacity",   value = 400 },
        { label = "UI_SpatialWell_RefillRate", valueKey = "UI_SpatialWell_RefillValue", valueArg = 2 },
        { label = "UI_SpatialWell_NoSkillRequired" },
        { label = "UI_SpatialWell_Immovable" },
    },

    -- ★ 行为回调：这就是必须在 Lua 而不能纯 YAML 的原因
    canPlaceAt = function(player, square, refugeData) return MSR.SpatialWell.CanPlaceAt(player, square, refugeData) end,
    canMoveTo  = function(player, square, refugeData, obj) return MSR.SpatialWell.CanMoveTo(player, square, refugeData, obj) end,
    createAt   = function(player, x, y, z, refugeData) return MSR.SpatialWell.CreateAt(player, x, y, z) end,
    find       = function(refugeData) return MSR.SpatialWell.Find(refugeData) end,
    countOf    = function(refugeData) return MSR.SpatialWell.IsBuilt(refugeData) and 1 or 0 end,
})
```

> **关键**：水井这条注册项只是**把现有函数包一层**，一行旧逻辑都不改。行为等价性由"包壳"保证。

### 3.3 面板改造：列表 + 详情（复用兑换面板那套渲染手法）

```
┌──────────────────────────────────────────────────────────────┐
│  定制                                                          │
├───────────────┬──────────────────────────────────────────────┤
│ ┌──┐ 空间水井  │  ┌──┐ 空间水井                                 │
│ │  │ 未建造    │  │  │ 一口与圣物相连的水井…                    │
│ └──┘           │  └──┘                                          │
│ ┌──┐ <建筑B>   │  状态: 未建造                                  │
│ │  │ 已建造    │  ┌─ 属性 ─────────┐ ┌─ 所需资源 ─────────┐  │
│ └──┘           │  │ 储水量   400   │ │ 核心      12 / 35  │  │
│               │  │ 恢复速度 2/小时 │ │ 铁管       0 / 4   │  │
│               │  │ 无需建造技能    │ │ 混凝土粉   1 / 1   │  │
│               │  │ 无法拆除        │ │ 空水桶     0 / 1   │  │
│               │  └────────────────┘ └────────────────────┘  │
│               │                              [ 选择位置 ]      │
└───────────────┴──────────────────────────────────────────────┘
```

- 左侧条目三态着色：**已建造**（蓝） / **材料够（可建，绿）** / **材料不足（变暗 + 右侧状态文字变红）**
- 按钮三态：`选择位置` / `已经建造`（灰） / 材料不足（灰）
- 材料行「有 n / 需 m」+ 红绿配色 —— 与兑换面板同一套，**已抽成公共计数助手 `client/MSR_ItemCount.lua`**（未抽渲染，两个面板的行使布局本就不同）

> ⚠️ **落地时发现的一个隐患（已修）**：材料行的**顺序**。旧面板用固定常量 `ITEM_ORDER` 决定顺序，而水井的成本来自 `MSR.SpatialWell.GetTransactionRequirements()`，其前几项是 `pairs` 遍历哈希得到的 —— **顺序不确定**。若直接渲染，材料行会逐帧跳动。为此注册表增加了 `costOrder` 字段（可选，指定类型顺序；缺省则按物品名排序），水井按原 `ITEM_ORDER` 固定，显示与重构前一致。

### 3.4 光标泛化

`MSR_SpatialWellCursor.Start(player, buildableId)` / `.StartMove(player, obj)`：

- `isValid(square)` → `buildable.canPlaceAt(player, square, refugeData)`
- `tryBuild(x,y,z)` → `MSR.BuildableLogic.Build(player, self.buildableId, x, y, z)`
- 移动时从**对象 ModData 的 `buildableId`** 反查注册表（旧档的井没有该字段 → 回落到 `isSpatialWell` 识别，保持兼容）

保持现有的**惰性派生**做法（`:1-3` 注释：原版 `ISBuildingObject` 在 `media/lua/server`，客户端早期拿不到），这个坑已经踩过并解决了，不要"优化"掉。

### 3.5 事务化建造/移动 `shared/MSR_BuildableLogic.lua`

照 `MSR_ExchangeLogic` 的骨架（同一个模子）：

```
Build(player, buildableId, x, y, z)
 ├─ 1. 取注册项；无 → 返回错误
 ├─ 2. canPlaceAt / countOf < maxPerRefuge 校验
 ├─ 3. cost = 按难度缩放（核心 D.core、其余 D.material）
 ├─ 4. Transaction.Begin(player, "BUILD_"..buildableId, cost)   ← 每建筑独立事务类型
 ├─ 5. validateAllocationForRequirements → consumeWithReceipt
 ├─ 6. buildable.createAt(...)                                   ← 生成对象
 ├─ 7. 成功 finalizeReceipt + Finalize + 写 customizations 索引
 └─   失败 refundReceipt + Rollback（材料原样退回）
```

**事务类型按建筑分开**（`BUILD_spatial_well` 等），这样两座不同建筑可以并发建造、互不阻塞（`Transaction.GetPending` 按 type 分键）。

### 3.6 右键菜单泛化

`MSR_Context.lua` 里把硬编码的 `md.isSpatialWell` 判定换成"**读对象 ModData 的 buildableId → 查注册表**"：

- 找到 → 加一条 `移动 <建筑名>`
- 找不到但带 `isSpatialWell` → 回落到井（保证旧档对象也能移动）
- 菜单文案：新增通用键 `IGUI_MoveBuildable`（带 `%1` = 建筑名）；**井继续沿用 `IGUI_MoveSpatialWell`** 以免改动既有翻译

## 7. 需要用户确认的三个决策

### 决策 1：多实例？
后续建筑是「每个庇护所只能建一个」（像井），还是「可以建多个」（如储物箱 ×N）？
- 单实例 → 索引 `customizations.<id> = {placed,x,y,z,t}`，**与现在完全一致**
- 多实例 → 索引 `customizations.<id> = { {x,y,z,t}, ... }`，面板要加「已建 n / 上限 m」显示
- **两者可共存**：由注册项的 `maxPerRefuge` 决定该建筑用哪种 shape（`1` 写单对象、其它写数组）

### 决策 2：面板要不要分类？
像兑换面板那样按分类分组（实用/储物/装饰），还是平铺一个列表？
- 建筑数量少（<6）平铺更简单
- 分类可以从注册项的 `category` 自动汇总，成本很低

### 决策 3：重构范围
- **A（推荐）只做数据驱动**：水井行为、翻译、存档全部原样，只是把代码泛化
- **B 顺便加功能**：把井也改成多实例 / 加"拆除"功能 / 加建筑升级等级
  - ⚠️ B 会牵动存档 shape 与 `MSR_RefugePower` 等既有逻辑，风险明显上升，建议**另开一轮**

## 8. 与前序工作的关系

- **与兑换系统（06）的关系**：无耦合。兑换是"扣料换物品"，定制是"扣料放建筑"，两者只在**渲染手法**上互相参考（材料行 have/need）。
- **与升级系统（05）的关系**：无耦合。但若将来要做"建筑的等级"（如储物箱容量升级），那就该走**升级系统**而不是定制系统 —— 这也正是水井/升级当初被分成两套的原因（见 `05-升级清单.md` §4）。
- **`media/lua/server/` 依然不能删**（见 `04-多人模式与单人的边界.md`）：水井的补水逻辑在 `MSR_SpatialWellServer.lua`，泛化后每个建筑若有服务端逻辑（如定时产出），仍会放在那里。
