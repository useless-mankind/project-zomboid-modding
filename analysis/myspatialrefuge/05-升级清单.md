## 0. 一句话

**升级共 13 条、52 个等级**，分 5 个分类，只有一条前置依赖。

但**「空间水井」不是升级**——它属于与升级**并列的另一套「定制（Customization）」系统**，没有等级、不在 `upgrades.yaml` 里、数据存在另一个表（`refugeData.customizations` 而非 `refugeData.upgrades`）。详见 [§4](#4-不属于升级的定制系统空间水井)。

| 级 | 材料（普通难度基准） | 中文描述 |
|:--:|:---|:---|
| L1 | 发电机×1 + 电线×10 + 核心50 | 在庇护所内安装发电机。为整片区域永久供电，无需加油也无需维修。 |

> **四个发电机型号任选**：`Base.Generator`（Lectromax）／`Base.Generator_Yellow`（Premium Technologies）／`Base.Generator_Blue`（ValuTech）／`Base.Generator_Old`，走 `substitutes` 机制。生成出来的实体**固定是 `Base.Generator`**，因为不记录消耗的是哪一款。
>
> **位置是固定的物理坐标**，不是等级效果：庇护所中心**北侧一格** `(centerX, centerY-1, centerZ)` `[文件] MSR_RefugePower.lua:48`。升级只决定"放不放"。
>
> **免维护的实现**：`EveryTenMinutes` → `MSR.RefugePower.MaintainPower` `[文件] MSR_RefugePower.lua:177` 把油与耐久拉满（`GENERATOR_FUEL` / `GENERATOR_CONDITION` = 100）、并保证 `connected` / `activated` 为真；发电机若丢失则原地重建。玩家侧完全无感，也永远不会触发原版发电机 20% 耐久以下的起火/爆炸判定。
>
> **维护门限是「区块已载入」，不是「玩家在庇护所内」**：原判据太窄——42.17 实测报告（[Active generator stops consuming fuel in player's absence](https://theindiestone.com/forums/topic/94905-4217-active-generator-stops-consuming-fuel-in-players-absence/)）证实发电机在区块载入期间**即使玩家在墙外也照样烧油**，那段窗口没人补油。现改为 `MSR.World.areAreaChunksLoaded(centerX, centerY, centerZ, 1)`（`[文件] MSR_RefugePower.lua:185-189`），顺带保证不会去碰未载入的区块。
>
> **不含照明**：B42 的 `IsoLightSource` / `cell:addLamppost` 方案已全部移除（灯是瞬态对象，不进存档，区块重载即消失；且维护逻辑从不补灯）。本升级只供电。
>
> ⚠️ **这条定义曾被工坊更新覆盖丢失**：上游 mod 的 `upgrades.yaml` 覆盖了本地版本，把 `refuge_power` 抹掉了；而 `MSR_RefugePower.lua` 是自建文件、上游没有，所以代码留了下来。2026-09-21 按 `reference/PZ42_物品ID参考表.md` §6 复原配方。

## 3. 机制说明（改升级前必读）

### 3.1 双数据源与覆盖顺序

1. 先加载 Lua 的 `MSR_UpgradeData.UPGRADE_DEFINITIONS`（含 `expand_refuge`、`debug_fail_upgrade`）
2. 再由 `upgrades.yaml` **覆盖/追加**同名条目 `[文件] MSR_UpgradeData.lua:196-230`

所以**改 yaml 里的同名条目会覆盖 Lua 定义**；`expand_refuge` 不在 yaml 里，只能改 Lua。

### 3.2 可替代材料（substitutes）

yaml 里的 `SRU_*` 物品是**占位锚点**（真实物品但从不掉落，`ItemType = base:literature`），实际消耗由 `substitutes` 指向的物品组承担。共 16 个组：

| 组名 | 条目数 | 组名 | 条目数 |
|:---|:--:|:---|:--:|
| `skillbooks_1` ~ `skillbooks_5` | 各 24 | `bedding_tier1` | 2 |
| `wristwatches` | 16 | `bedding_tier2` | 22 |
| `alarm_clocks` | 1 | `entertainment_tier1` | **151** |
| `vehicle_tires` | 9 | `entertainment_tier2` | 14 |
| `medical_tier1` | 4 | `pain_relief_tier1` | 2 |
| `medical_tier2` | 2 | `pain_relief_tier2` | 2 |

语法：`substitutes: [ $组名 ]`（`$` 也可写 `*`），支持 `$组名+Base.X` 追加单个物品。**不支持 YAML 锚点**（解析器是自己写的，见 [`03-配置数据与升级体系.md`](03-配置数据与升级体系.md)）。

> ⚠️ 这也是当年 **CN 翻译缺 13 条** 的根源：这些 `SRU_*` 占位物要在「所需物品」面板显示名字，而中文包里没有它们。**已于 2026-09-21 补齐**（译名用「任意X级XX」措辞，因为 substitutes 接受该类别该级的**任意**物品），详见 [`00-现状整理.md`](00-现状整理.md) §5.1 第 1 条。

### 3.3 效果走两条不同的路 ⚠️

| 路径 | 涉及效果 | 说明 |
|:---|:---|:---|
| **进 `EffectSystem`** | `refugeWoundRecoveryMultiplier`、`refugeSleepFatigueMultiplier`、`refugeMentalRecoveryMultiplier`、`refugeStiffnessRecoveryMultiplier` | 只有这 4 个恢复类乘数注册进了效果系统（`EffectRegistry` 里就这 4 个） |
| **绕过效果系统** | `readingSpeedMultiplier`、`refugeCastTimeMultiplier`、`relicStorageCapacity`、`corePickupRadius`、`refugeCropGrowthTimeMultiplier`、`vehicleTeleportEnabled`、`refugeSize` | 由各子系统**直接读 `getPlayerActiveEffects`** |

**加「新效果型升级」时要知道自己该挂哪条**——挂错的表现是「升级买了但没效果」。

### 3.4 购买流程（含事务）

```
canPurchaseUpgrade（校验依赖满级 + 材料够）
  → Transaction.Begin（锁定所需物品，记账）
  → executeAuthoritative（校验 → 最大流匹配 substitutes → 权威扣料）
  → 成功 Finalize / 失败 Rollback（逆序回填：原容器 → 背包 → 地面）
```

单机也走这一整套（防的是自己的逻辑 bug），只是不跨进程 `[文件] MSR_UpgradeLogic.lua:408-437`。

## 4. 不属于升级的定制系统：空间水井

**结论：水井不是升级，是「定制（Customization）」系统的第一个（也是目前唯一一个）条目。** 它在同一个窗口的**另一个标签页**里，代码路径、数据结构、事务类型全都独立。

> **目前定制标签里只有水井一个条目**，但数据层是**为多个预留**的——迁移代码的注释原文写着 `Add customizations table for Spatial Well and future objects` `[文件] MSR_Migration.lua:250`，且该表初始化为空表 `[文件] Data.lua:408`。**UI 层则没有泛化**，详见 [§4.6](#46-目前只有一条但扩展性分两层)。

### 4.1 玩家侧流程

```
右键圣物 →「管理庇护所」→ 窗口切到「定制」标签
  →「选择位置」按钮（材料不足则该按钮灰掉）
  → 进入放置光标，在庇护所内点选位置
  → 校验通过 → 扣料 → 生成实体
成功提示：「空间水井已与庇护所连接。」
```

### 4.2 与升级的结构对比

| 维度 | 升级 | 空间水井（定制） |
|:---|:---|:---|
| 数据位置 | `refugeData.upgrades[id] = 等级` | `refugeData.customizations.spatialWell = {placed,x,y,z}` |
| 定义位置 | `upgrades.yaml` + Lua | `Config.SPATIAL_WELL`（`00_core/Config.lua:65-85`） |
| 等级概念 | ✅ 1–8 级 | ❌ 一次性建造，只能移动 |
| 事务类型 | `UPGRADE` | `SPATIAL_WELL_BUILD` `[文件] MSR_SpatialWell.lua:20` |
| 落地形式 | 改地图 / 改玩家状态 | **世界实体** `Base.MSRSpatialWell` |
| 移动 | 不适用 | ✅ 可移动，冷却 **30 秒** |
| 拆除 | 不适用 | ❌ **无法拆除**（UI 明写 `UI_SpatialWell_Immovable`） |

### 4.4 关键结论：水井没有等级门槛

`CanPlaceAt` 只检查三件事 `[文件] MSR_SpatialWell.lua:199-232`：

1. 玩家在**自己的庇护所范围内**
2. 该庇护所**还没建过水井**
3. 落点位置合法（不在墙上/障碍上等）

**没有**「需要某升级满级」「需要达到某 tier」「需要建造技能」之类的门槛。所以**理论上开局就能造**——只要凑得齐 35 核心 + 4 铁管 + 1 混凝土粉 + 1 空桶。玩家侧的体感差别来自**材料获取难度**，不是系统门控。

> 写新内容时注意这个区别：**「看起来像解锁」的往往只是材料门槛，不是系统门控。**

### 4.5 已知隐患

`EnsureForRefuge` 在实体丢失后重建水井时，水量会退回初始值 40，**已存的水会丢** —— 见 [`03-配置数据与升级体系.md`](03-配置数据与升级体系.md) §6。

### 4.6 目前只有一条，但扩展性分两层

> ✅ **2026-09-21 已重构**：本节描述的「UI 层未泛化」问题**已解决** —— 定制系统改成了数据驱动（注册表 + 泛化光标 + 列表式面板），**加新建筑不再需要动 UI**。详见 [`07-定制系统重构设计.md`](07-定制系统重构设计.md)。
> 下表的「UI 层」一行是**重构前的状态快照**，保留用于理解当时的取舍；当前现状以 07 为准（数据层与 UI 层都已泛化，只有放置光标仍需按建筑的落位规则提供回调）。

**结论：定制里现在只有水井一个，且 UI 层是硬编码的单条目，不是列表。**

| 层 | 现状 | 加第二个可建造物时要做什么 |
|:---|:---|:---|
| **数据层** ✅ 已泛化 | `refugeData.customizations` 是**空表**，注释明写为 future objects 预留；写入方式为 `customizations.<键> = {...}` | 直接加新键，如 `customizations.workbench` —— **不需要改结构、不需要新迁移** |
| **UI 层** ❌ 未泛化 | `MSR_CustomizationPanel`（197 行）**整块写死水井**：唯一按钮 `UI_SpatialWell_Build`、图标 `media/ui/SpatialWell_64x64.png`、文案 `UI_SpatialWell_Name/_Description`、属性行（储水量/恢复速度/无需技能/无法拆除）、材料行循环 `ITEM_ORDER`、`refresh()` 直接问 `MSR.SpatialWell.IsBuilt`、点击直接 `MSR_SpatialWellCursor.Start` | **需要重构面板**：从「单条目」改成「列表 + 选中详情」，可参照升级标签已有的 `SRU_UpgradeGrid` + `SRU_UpgradeDetails` 三栏模式 |
| **放置** ⚠️ 每次一个 | 只有一个通用放置光标 `MSR_SpatialWellCursor` | 若新物件放置规则不同，要么给它加参数，要么另写一个 cursor |
| **事务** ✅ 可复用 | `SpatialWell.TRANSACTION_TYPE = "SPATIAL_WELL_BUILD"` | 新模式加一个类型常量即可（事务机制本身是通用的） |

**证据**：`[文件] MSR_CustomizationPanel.lua:51-63`（唯一按钮）、`:139`（硬编码图标）、`:145-149`（硬编码文案）、`:167-175`（硬编码属性行）、`:184-188`（材料行）、`:70/:98`（直连 `MSR.SpatialWell`）。

> **给后续开发的提示**：如果只加 1–2 个可建造物，最快是**照抄 `MSR_CustomizationPanel` 再写一个专用面板**；如果打算做成一整套「建造目录」，就该先把它重构成数据驱动的列表，否则每加一个物件都要复制一遍 197 行。

## 5. 扩展指引

| 想做的事 | 改哪里 | 注意事项 |
|:---|:---|:---|
| **加一条普通升级** | `upgrades.yaml`（文件末尾有注释掉的模板，`upgrades.yaml:1009-1036`） | 要同时补 **CN 与 EN** 的 `UI_Upgrade_<X>` 与 `UI_Upgrade_<X>_L<n>`（本工程只保这两种语言） |
