## 3. 工程架构

### 3.1 全局命名空间与模块系统

- 全局 `MSR` 表，`MSR.register(name)` 幂等注册：已加载则返回 `nil`，调用方 `if not X then return MSR.X end` 防重载 `[文件] 00_core/00_MSR.lua:43-56`。
- **例外**：`Transaction` / `InventoryAuthority` / `Validation` / `UpgradeData` 不走 `register`，直接赋值 `MSR.X` `[文件] 03 报告 §1`。
- 三个全局别名：
  - **`K`** = KahluaCompat，补齐 Kahlua 缺失的 `next()` / `os.*` / `rawget`，并封装 Java ArrayList 的 0 基迭代 `[文件] 00_core/KahluaCompat.lua`
  - **`L`** = Logging，`L.logger("模块名")` → `debug/info/warning/error`；调试开关 `L.isDebug()` 依赖 `getDebug()`
  - **`D`** = Difficulty，`D.core()` / `D.material()`（**两者完全等价**）/ `D.cooldown()` / `D.positiveValue()`…
- 难度映射：沙盒 1–5 档 → `coreCost/cooldown = 0.5/0.75/1/1.5/2`，`effectPower = 1.2/1.1/1/0.9/0.8` `[文件] 03 报告 §1`。

### 3.2 加载链

```
shared  : MSR_Shared.lua → 00_core/00_MSR.lua
          → require 00_core/{KahluaCompat, Logging, Env, Config, Data, Utils, Difficulty, Events, Validate}
          → 各业务模块
client  : MSR_Main.lua（+ Migration / Shared / PlayerMessage / XPRetention / Death / RestorationEffects）
server  : MSR_Server.lua（显式 require 20+ 个依赖）
```

> **服务端必须显式 `require` 的理由**（`MSR_Server.lua:1-2` 原文注释）：专用服务器上「自动目录扫描」不保证在 server 代码运行前完成。**这是写服务端 mod 的重要坑。**
>
> 但仍有 4 个文件靠自动加载：`AdminHandler`、`AutomaticCorePickup`、`FertileResonance`、`ZombieCoreDrops` `[文件] 01 报告 §1`。

### 3.3 环境判定

集中在 `00_core/Env.lua`（带缓存）：

| 环境 | `isServer` | `isClient` | 可改数据 |
|:---|:---|:---|:---|
| 单机 | false | false | ✅ |
| 服务器进程（专用/Coop 主机） | true | false | ✅ |
| 客户端进程（MP/Coop） | false | true | ❌ |

> 源码注释特别强调：**Coop 主机也是两个独立进程**，`(true,true)` 实际不出现 `[文件] 00_core/Env.lua:97-111`。`canModifyData()` = 单机或服务端。

### 3.4 数据模型与持久化

```
ModData.getOrCreate("MySpatialRefuge")
├── .Refuges[username] = refugeData        ← 主数据，按玩家用户名索引
└── .ReturnPositions[username]             ← 出避难所的回程坐标
```

`refugeData` 字段（序列化白名单见 `Data.lua:38-60`）：
`refugeId`（= `"refuge_"..username`）、`username`、`centerX/Y/Z`、`tier`、`radius`、`areaOffsetX/Y`、`relicX/Y/Z`、`upgrades`、`customizations`、`createdTime`、`lastActiveTime`、`lastExpanded`、`dataVersion`；运行期追加 `roomIds` / `roomData` / `roomBounds`、`isOrphaned` / `originalOwner` / `inheritedFrom`。

**坐标池**：基点 `(1000, 1000, 0)`，槽位间距 50，**20×20 = 400 个槽位**；`col = slot % 20`、`row = slot // 20`。每个避难所**锚定在一个「圣物（Sacred Relic）」实体上**，有效几何 = 圣物中心 ± `areaOffsetX/Y` `[文件] 00_core/Config.lua:12-16` / `01 报告 §2`。

**存档版本迁移**：`CURRENT_DATA_VERSION = 8`，`MSR_Migration.lua` 是 **Alembic 式** `MIGRATIONS[版本] = 迁移函数`，v1→v8 逐级迁移（v1 是 per-player ModData，v2 起改全局表；v7→v8 是引入 `areaOffsetX/Y`）`[文件] 01 报告 §4`。**这是整个 mod 最值得学的工程实践**——存档格式演进有版本号、有迁移链、失败可回滚。

### 3.5 客户端 ↔ 服务端协议

**自定义协议**，命名空间 `"SpatialRefuge"`，命令常量集中在 `00_core/Config.lua:113-149`（约 25–37 个）。

### 3.7 升级体系与事务

**双数据源**：

1. Lua 主定义 `MSR_UpgradeData.UPGRADE_DEFINITIONS`（`MSR_UpgradeData.lua:26`）
2. `upgrades.yaml`（**1036 行**）覆盖 / 扩展同名条目（`MSR_UpgradeData.lua:196-230`）

`upgrades.yaml` 结构：`itemGroups`（12 个可复用物品组）+ `upgrades`（11 条 / 43 级）。

```yaml
upgrades:
  faster_reading:
    id / name(翻译键) / icon / category / maxLevel / dependencies
    levels:
      1:
        description: UI_Upgrade_FasterReading_L1
        effects:   { readingSpeedMultiplier: 0.85 }
        requirements:
          - type: Base.MagicalCore
            count: 10
          - type: Base.SRU_SkillBookTier1
            count: 5
            substitutes: [ $skillbooks_1 ]     # $组名 展开；支持 * 前缀与 +Base.X 追加
```

> 文件末尾自带一份**注释掉的「新增升级模板」**（`upgrades.yaml:1009-1036`），加新升级直接照抄。
> `dependencies` 只有 `refuge_basement → [expand_refuge]` 一条非空——前置分两层：依赖升级需满级 + 逐级物品需求 `[文件] 03 报告 §3`。
> 数量按难度缩放，唯一入口是 `getNextLevelRequirements`（核心走 `D.core`，其余走 `D.material`）。

**事务机制** `MSR_Transaction.lua`：分配清单（journal）式**两阶段锁定**，不做世界快照。

```
canPurchaseUpgrade → Transaction.Begin（锁料，写 journal + 玩家 ModData 跨重连）
   → executeAuthoritative（validate → 最大流匹配 substitutes → InventoryAuthority.consumeWithReceipt 原子扣料 + receipt）
   → Commit → Finalize（MP 清锁）/ Rollback（失败 refund 逆序回填：原容器→背包→地面）
```

四态 `PENDING / COMMITTED(SP) / FINALIZED(MP) / ROLLED_BACK`，所有入口以 `status == PENDING` 为门 → **幂等防重放**；服务端每 10 秒批检超时自动回滚 `[文件] 03 报告 §4`。

**效果系统** `00_core/EffectSystem.lua` + `EffectRegistry` + `EffectProvider`：Provider（契约工厂）→ Registry（按玩家存 `效果名 → {sources, total, stacking}`，`ADDITIVE`/`MAXIMUM` 合并）→ System（`updatePlayer`：clear → 各 provider 重算 → recalculate）。

> ⚠️ **实际只登记 4 个效果**（全是庇护所恢复乘数：`refugeWound` / `SleepFatigue` / `Mental` / `StiffnessRecoveryMultiplier`，全 MAXIMUM、默认 1.0）；其余升级效果（阅读速度、施法时间、遗物容量、核心拾取半径）**完全绕过 EffectSystem**，直读 `getPlayerActiveEffects` `[文件] 03 报告 §5`。想加"效果型"升级时要知道走哪条路。

### 3.9 地图生成与扩建

- 真正建图在 `MSR_RefugeGeneration`：`IsoThumpable.new(cell, square, sprite, isNorth, {})` 建边界墙与圣物，圣物 `setIsContainer(true)` + `setBlockAllTheSquare(true)`，清树用 `getTree()` / `toppleTree()`。
- 扩建在 `MSR_RefugeExpansion`（只编排，不建图）：Commit 后依次 存盘 → 协调上层 → 清树 → 清僵尸 → 生成地下室 → 恢复房间 → 完整性校验，失败 `MSR.delay(30, …)` 重试。
- 地下室：`centerZ - 1`；地板 `square:addFloor("floors_exterior_street_01_17")`，缺格用 `IsoGridSquare.new` + `cell:ConnectNewSquare` 造稀疏层，楼梯 `IsoObject.new`。
- 边界用 `MSR_BoundaryReconciler`：对 `isRefugeBoundary` 对象做**保留/收养/删除/新建四路协调**，用 `refugeSlotKey` 防跨槽误删。
- 网络同步统一走 `helpers/World.lua` 的 `addObject` / `removeObject`（按环境分派 `transmitAddObjectToSquare(obj,-1)` / `AddSpecialObject` 等）。

### 3.10 调试设施（可以直接用）

- `MSR_AdminCommands` + `MSR_AdminHandler`：修复、回收、传送等管理命令，`isAccessLevel("admin")` 鉴权。

## 6. 与手册 `docs/` 的关系，以及可回填的结论

手册里已有一处实证**就是这个 mod**：`docs/06-翻译.md:9` 写的「实测一个同时带 `42.14/` 与 `42.15/` 两个版本目录的工坊 mod，前者是 `ItemName_CN.txt`、后者是 `ItemName.json`」。另外 `reference/PZ42_物品ID参考表.md` 第六节整节是从它的 `upgrades.yaml` 抽出来验证的。

读完代码后，**建议回填手册的三条**（尚未动手，等你点头）：

1. **版本目录命名可以精确到 minor**：`docs/03` 第 42 行写「`42` 对 `42.0`~`42.14`」，但本 mod 用的是 `42.14/` 且 `versionMin = 42.14`、`versionMax = 42.14`。更准确的说法是「目录名 = 该目录 `mod.info` 的 `versionMin` 值，可精确到 minor」。
2. **`tiledef` ID 要按版本目录分别写**：同一 mod 的 42.14 用 `13232`、42.15 用 `5933`。`docs/03` 只说「ID 会冲突、需查登记表」，没提跨 build 移植的这条实操。
3. **手册的空白区**（本 mod 全部用到，是 B42 大型 mod 的真实套路，可增补一章「大型 mod 工程结构」）：
   - 多模块工程组织与 `MSR.register` 式幂等加载
   - `GlobalModData` 持久化 + **数据版本迁移**（Alembic 式）
   - 自定义客户端-服务端命令协议（命名空间 + 分发器 + 鉴权 + 限流）
   - 自定义事件：`LuaEventManager.AddEvent` + `triggerEvent`
   - **从 mod 目录读文件**：`getModInfoByID` / `getModFileReader` 在 B42 需要试 `\modId` 反斜杠前缀；且 `getModFileReader` 对不存在的 mod 会抛 **Java NPE，`pcall` 抓不住**，必须先校验存在性（`CUI_FileUtils.lua:116-123` 的注释就是这么写的）；PZ 无内置 YAML 解析器，本 mod 自带 21 KB 的 `CUI_YamlParser`
   - 服务端 mod 必须显式 `require`（专用服务器目录扫描时序不可靠）
