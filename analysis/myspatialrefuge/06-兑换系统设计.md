# 06 · 「兑换」系统设计与实施方案

> **状态**：**设计稿 —— 待确认后实施，尚未写任何代码**
> **决策基线**（2026-09-21 与用户确认）：
> 1. 兑换项 **可无限重复**（不设限购）
> 2. **只做单机**（不实现多人命令协议分支）
> 3. 列表 **要分类**
> 4. 不灭武士刀 **合并进本 mod**，且 **保留原物品 ID** `PristineKatana.PristineKatana`
>
> **路径**均相对 `mods/myspatialrefuge/`。`[文件]` = 已核实的源码事实；`[推断]` = 待实测确认。

## 1. 目标与范围

### 1.1 要做的事

在现有「升级 / 定制」两个标签之外，加第三个标签 **「兑换」**：消耗「核心 + 若干物品」换取指定物品，条目可无限重复。

两个目标用例（用户提出）：

| 用例 | 输入 | 输出 | 定位 |
|:---|:---|:---|:---|
| 断武器翻新 | 断棒球棍 + 核心 | 新棒球棍（满耐久） | 可重复的**循环补给** |
| 珍品兑换 | 大量核心 | 不灭武士刀 | 一次性获取（该武器永不损毁，换一次就够） |

### 1.2 明确不做（防止范围蔓延）

| 不做 | 原因 |
|:---|:---|
| ❌ 限购 / 冷却 / 每日次数 | 用户选了"可无限重复" → **不需要在 `refugeData` 记状态** → `CURRENT_DATA_VERSION` 保持 8，**不加迁移** |
| ❌ 多人命令协议分支 | 用户只玩单人 → 全走 `hasServerAuthority()` 为真的本地路径，`Config.COMMANDS`、`server/MSR_Server.lua`、`client/MSR_ServerCommandRouter.lua` **一行都不改** |
| ❌ 跨 mod 软探测 | 武士刀已并入同一 mod，物品必然存在 |
| ❌ 改动升级 / 定制 / 事务 / 网络 / 存档 任何既有逻辑 | 新系统**只读复用**它们，不修改 |

## 4. 数据设计：`media/lua/shared/exchanges.yaml`

### 4.1 字段规范

```yaml
itemGroups:            # 可选，与 upgrades.yaml 同语法（$组名 展开，支持 +Base.X 追加）
  <组名>:
    - Base.X

exchanges:
  <条目id>:
    id: <同键名>                     # 必需，全局唯一
    name: UI_Exchange_<X>            # 必需，翻译键（列表与详情标题）
    description: UI_Exchange_<X>_Desc # 可选，详情描述翻译键
    icon: <贴图名>                    # 图标：物品图标名（不带 Item_ 前缀）或 media/ 下路径
    category: <分类键>                # 必需（要分类），如 weapon / tool / supply / treasure
    sortOrder: 10                    # 可选，同分类内排序
    cost:                            # 必需，复用现有 requirement 结构
      - type: Base.MagicalCore
        count: 15
        # substitutes: [ $组名 ]       # 可选：可替代材料
        # predicate: <函数名>          # 可选：按条件筛选（见 4.3）
    reward:                          # 必需，新概念
      - type: Base.BaseballBat
        count: 1
        fullCondition: true          # 可选，默认 false；true = 造出来就是满耐久/满锋利度
```

**设计原则**：`cost` 与升级的 `requirements` **逐字段同构** → 可以直接 `Transaction.Begin(player, "EXCHANGE", cost)`，**不需要任何转换层**。

### 4.3 ⚠️ 「断掉的武器」的两种判定路径（实施前必须确认）

PZ B42 里武器断掉有两条可能路径：

| 路径 | 机制 | 证据 | 我们的写法 |
|:---|:---|:---|:---|
| **(a) 断成另一个物品** | 物品参数 `OnBreak = OnBreak.Xxx`，由 Lua 决定产物，断开物标 `DisplayCategory = BrokenWeapon` | `[文件]` Michonne's Katana：`items_Michonne.txt:62,66,108` + `OnBreak_Michonne.lua:9` | 直接用 `type: Base.BaseballBat_Broken` |
| **(b) 只是耐久归零，物品类型不变** | 靠 condition 判断 | — | `type: Base.BaseballBat` + `predicate` |

**实施第一步就该确认**：`getScriptManager():getItem("Base.BaseballBat_Broken")` 是否存在。
- 存在 → 走 (a)，一切照旧
- 不存在 → 走 (b)，需要一个 predicate 函数（可仿 `SpatialWell.IsEmptyBucket`）

**已验证的事实**：原版存在修复配方 `fixing Fix Baseball Bat { Require : BaseballBat, ... }` `[文件] .research/Zomboid-Modding-Guide/scripts/README.md:186-194`，说明 `Base.BaseballBat` 是真实 ID；**但断开物的具体 ID 未能离线确认**（PZ Wiki 抓取被 Cloudflare 拦，HTTP 403）。

### 5.2 `shared/MSR_ExchangeLogic.lua`（新增，对标 `MSR_UpgradeLogic`）

```
MSR.ExchangeLogic.Execute(player, exchangeId)
 ├─ 1. 取定义；无效则返回 false, err
 ├─ 2. cost = ExchangeData.getCost(exchangeId, player)   ← 已按难度缩放
 ├─ 3. transaction, err = Transaction.Begin(player, "EXCHANGE", cost)
 │      失败（含"材料不足"/"已有同类型事务"）→ 返回 false, err
 ├─ 4. allocation = 由 transaction.lockedItems 生成（同 purchaseUpgradeSP 的 allocationFromTransaction）
 ├─ 5. ok = UpgradeLogic.validateAllocationForRequirements(cost, allocation)
 │      false → Transaction.Rollback → 返回 false, err
 ├─ 6. receipt = InventoryAuthority.consumeWithReceipt(player, sources, allocation, IsItemAvailable)
 │      nil → Rollback → 返回 false, err
 ├─ 7. 发奖 GiveRewards(player, reward)                    ← 见下
 │      失败 → refundReceipt + Rollback → 返回 false, err
 ├─ 8. finalizeReceipt(receipt) + 成功提示
 └─ 9. Transaction.Finalize(player, transaction.id)
```

**`GiveRewards(player, reward)` 的实现要点**：

```
for each entry in reward:
    item = instanceItem(entry.type)
    if not item → 记录失败（不要静默跳过）
    if entry.fullCondition → MSR.ItemCondition.MakePristine(item)
    if entry.count > 1 → 循环创建
    放入玩家背包：player:getInventory() ；hasRoomFor 判定
      装不下 → 落到玩家脚下：player:getSquare():AddWorldInventoryItem(item, 0.5, 0.5, 0, true)
```

> **顺序铁律**：**先扣料成功、再发奖**；发奖任何一步失败都必须 `refundReceipt` + `Rollback`。这个骨架就是 `UpgradeLogic.executeAuthoritative`（`shared/MSR_UpgradeLogic.lua:270-362`）的形状。

**debug 兑换项**：照现有 `debug_fail_upgrade`（故意失败的升级，用于测回滚）的思路，加一个 `debug_fail_exchange`（`debugOnly: true`，扣料后必定失败），**用来验证回滚路径正确**——这是这个 mod 已验证有效的工程习惯，值得沿用。

## 6. 关键实现细节与坑

| # | 坑 | 处理 |
|:--|:---|:---|
| 1 | **武器产物可能是残血货** | `fullCondition: true` → 走三层恢复（本体/刃部/锋利度）；对不适用的层自动跳过 |
| 2 | **锋利度脚本控不了** | 只能 `applyMaxSharpness()`（手册[附录 B.4](../../docs/10-数据获取与研究设施.md)） |
| 3 | **背包可能满** | `hasRoomFor` 判定 → 满了丢脚下，**绝不能静默丢弃** |
| 4 | **UI 计数不支持 predicate** | `getCountForRequirement` 只处理 `substitutes`（`[文件] MSR_UpgradeItemCache.lua:112-129`）。若走 4.3(b) 的 predicate 路线，需要新增一个 `CountMatchingRequirement(player, requirement)`：有 predicate 时退回逐物品扫描 |
| 5 | 事务类型冲突 | 用 `"EXCHANGE"`；`Transaction.GetPending` 按 type 分键，**与 `"UPGRADE"` / `"SPATIAL_WELL_BUILD"` 互不干扰** |
| 6 | 同类型事务只能有一个 | `Transaction.Begin` 会拒绝并发的同类型事务（返回 "Transaction already in progress"）→ UI 上兑换按钮要防连点（升级窗口已有 `_pendingUpgrade` 防双击的先例） |
| 7 | 难度缩放 | cost 走 `D.core()` / `D.material()`，与升级一致，**不要在 yaml 里写缩放后的数** |
| 8 | 图标来源 | 优先复用物品图标名（`icon: BaseballBat` → `Item_BaseballBat.png` 由引擎解析）；这与 mod 里既有的 `icon: media/textures/Item_Pocketwatch.png` 写法并存，实施时统一一种 |
| 9 | 兑换窗口的隐含约束 | 窗口要求圣物在 **3 格内**（`_closeDistance = 3`）→ "必须在庇护所内兑换"免费获得 |
