# 08 · 调试免费模式（Debug Free Mode）设计

> **状态**：✅ **已实施**（2026-09-21）。代码提交在 mod 内层仓库 `455989e`。**与本文档的偏差见 [§8 实施记录](#8-实施记录实际落地)**
> **需求**：debug 模式下，**升级 / 兑换 / 定制** 三类操作都可以**不消耗材料**直接生效。
> **已确认的三个决策**：① 开关 = **点 UI 上那行字切换**（不用聊天命令）② 视觉反馈 = **面板上加一行「调试：免费」**（这行同时就是开关）③ 范围 = **只免材料消耗**（放置合法性、实例上限照旧）
> **现有 debug 判定**（沿用，不新造轮子）：`MSR.Env.isDebugEnabled()`（`00_core/Env.lua:78-83`，依次查 `getDebug()` / `getCore():getDebug()` / `isDebugEnabled()`）。mod 里已有 3 处用它做 debug 门控（`MSR_UpgradeData.lua:267`、`MSR_UpgradeLogic.lua:373`、`MSR_Server.lua:731` 的 `debugOnly` 过滤）。
> **路径**均相对 `mods/myspatialrefuge/`。`[文件]` = 已核实的源码事实。

## 1. 核心结论先说：**不能只在事务内核拦，要分两层**

需求看着像"把消耗去掉就行"，但代码里 **"能不能点"和"点了能不能成"是两套独立的判定**：

```
玩家点按钮
   │
   ├─ ① UI 闸门：按钮 enable 与否  ← 各系统各自的"计数"函数（只读）
   │
   └─ ② 执行闸门：Transaction.Begin 锁料 → 数量不够就直接失败（真扫背包）
```

只改执行层 → **按钮一直是灰的，根本点不了**；只改 UI 层 → **点了报"材料不足"**。所以必须两层都覆盖。

**推荐架构（关键取舍）**：

| 层 | 做法 | 为什么不选另一种 |
|:---|:---|:---|
| ① UI 计数层（只读） | 在**三个计数函数**里短路，返回"刚好够" | — |
| ② 执行业务层 | 在**四个业务入口**把成本替换成空表，跳过 `Begin`/扣料 | ❌ 不在 `Transaction` / `InventoryAuthority` 内核里塞"免费"逻辑 —— 那是保证不复制不丢物品的核心，混进作弊语义风险最高，且会意外影响联机路径 |

**一句话**：**让计数撒谎 + 让业务层跳过扣料，事务内核一行不改。**

### 2.1 UI 闸门（3 个计数来源，1 个共用）

| 升级 | `MSR_UpgradeWindow:canCurrentlyUpgrade`（防连点/刷新时也走） | `UpgradeLogic.canPurchaseUpgrade` → `hasRequiredItems` → `getAvailableItemCount` → `Transaction.GetSubstitutionCount`（**权威计数**） | `MSR_UpgradeWindow.lua:451-455`、`MSR_UpgradeLogic.lua:108-123` |

### 2.2 执行闸门（4 个业务入口，全部先 `Transaction.Begin`）

| 系统 | 入口 | 现状 |
|:---|:---|:---|
| 升级（单机） | `UpgradeLogic.purchaseUpgradeSP` | `if requirements and #requirements > 0 then Begin(...) end` —— **已经有"空需求=不建事务"的分支** `[文件] MSR_UpgradeLogic.lua:415-423` |
| 兑换 | `ExchangeLogic.Execute` | `cost` 非空则 `Begin` → `validate` → `consumeWithReceipt` |
| 通用建筑 | `BuildableLogic.GenericBuild` | `if #cost > 0 then Begin → validate → consume end` —— **已有空成本分支** |
| 水井 | `SpatialWell.RequestPlacement` | ⚠️ **无条件** `Begin(player, TRANSACTION_TYPE, GetTransactionRequirements())`，失败即 `SPATIAL_WELL_MISSING_RESOURCES` `[文件] MSR_SpatialWell.lua:527-543` |

> **好消息**：升级 / 兑换 / 通用建筑**三条已经有"成本为空就跳过事务"的既有分支**，只要在成本计算处替换成空表即可，逻辑天然被复用。
> **唯一需要动结构的是水井**（它无条件 Begin），约 8 行改动。

## 3. 推荐设计

### 3.1 新增 `00_core/FreeMode.lua`（唯一开关，全局可查）

```lua
MSR.FreeMode = {
    _override = nil,   -- true/false 手动覆盖；nil = 跟随 debug 模式
}

--- 是否处于"免费"状态
function FreeMode.IsActive()
    if FreeMode._override ~= nil then return FreeMode._override end
    return MSR.Env.isDebugEnabled() == true     -- 与 debugOnly 用同一个判定
end

--- 会话内手动开关（不持久化，避免"作弊模式卡在开"）
function FreeMode.SetOverride(value)   -- true / false / nil(恢复跟随 debug)
    FreeMode._override = value
end

--- ★ 业务层统一入口：免费时返回空表，否则原样返回
function FreeMode.EffectiveCost(cost)
    if FreeMode.IsActive() then return {} end
    return cost
end

--- ★ UI 层统一入口：免费时返回"刚好够"，让按钮亮起且显示 35/35 而不是天文数字
function FreeMode.EffectiveHave(req)
    local need = (type(req) == "table" and tonumber(req.count)) or 1
    return need
end
```

**加载位置**：加进 `00_core/00_MSR.lua` 的 require 列表（排在 `Env` 之后）。这样全工程任何地方都能直接 `MSR.FreeMode`，不必每个文件再 require —— 与 `K` / `L` / `D` 同级的基础设施。

### 3.2 覆盖点清单（7 处小改，事务内核零改动）

| # | 文件 | 改动 | 覆盖 |

### 3.3 开关命令（复用现有 `/msr`）

mod 已有 `/msr` 斜杠命令框架（子命令 `help/stats/list/info/inactive/purge/delete/goto/scan`，单机本地执行、联机走 `AdminCommand`）`[文件] client/MSR_SlashCommands.lua:233-239`、`server/MSR_AdminCommands.lua`。

新增一个子命令：

```
/msr free            查看当前状态（debug=on / 覆盖=on|off）
/msr free on         强制免费（即使不在 debug 模式）
/msr free off        强制不免费（便于在 debug 下测试真实材料流程）
/msr free auto       恢复跟随 debug 模式
```

**为什么要 `off`**：你会**开着 `-debug` 玩**（为了控制台看报错），如果免费自动生效，就再也测不了真实的材料链路。有个 `off` 才两全。

## 5. 风险与对策

| 风险 | 等级 | 对策 |
|:---|:---|:---|
| **误改事务内核导致物品复制/丢失** | — | **本方案不碰** `Transaction` / `InventoryAuthority` 任何一行 |
| "按钮亮但点了报错"（两层不一致） | 中 | 覆盖矩阵逐项自测；执行的最终裁决仍在 `Begin`/`consume`，不一致只会表现为失败提示，不会产生脏数据 |
| 免费模式下事务仍要正确"关账" | 中 | 三条已有空成本分支会**完全跳过事务**（`transaction == nil`）；水井那条要确保 `Rollback/Commit` 有 nil 守卫 |
| 视觉上看不出免费，以为 mod 算错了 | 中 | 见 [§7 决策 2](#7-需要用户确认的三个决策) |
| 联机下客户端免费、服务端拒绝 → 不同步 | 低 | 你只玩单机；执行闸门都在**有本地权威**的一侧，联机时服务端会正常拒绝（表现为失败提示，不会刷物品） |
| 以后新增第 5 类消耗系统忘了接 | 低 | `FreeMode.EffectiveCost` 命名自解释；文档 + `FORK-NOTES` 扩展入口表注明 |

## 9. 前序决策记录（保留）

### 决策 1：开关方式
- **A（最终选）**：`-debug` 下**自动免费**，UI 上点那行字可临时关掉以测试真实流程
- B：只有显式开启才免费（debug 只是前提之一）
- C：自动 + 加一个快捷键（如 F10）切换

### 决策 2：视觉反馈
免费时如果不提示，你自己会怀疑"是不是 mod 算错了"。三种做法：
- **A（最终选）**：材料行仍显示 `35 / 35`（绿），但窗口上有一行「调试：免费」
- B：材料行显示 `∞ / 35`（最显眼，但要改两处渲染）
- C：不加任何提示（完全静默，最省事但容易自己搞混）

### 决策 3：范围
- **A（最终选）**：**只免材料消耗**。放置合法性、实例上限、庇护所范围等判定**一律照旧**
- B：连**实例上限**也免（比如想建 10 个水井做布局测试）—— 需额外改 `BuildableData.CanPlaceAnother`
- C：连**放置合法性**也免（想在任何地方放东西）—— 风险高，会绕过庇护所归属校验，建议不做
